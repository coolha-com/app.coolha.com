### 2.3 RWA Discovery

目标：发现和研究不同发行方、市场与链上的代币化资产，并提供透明、可核验的来源信息。

候选资产类型： - 代币化股票 - 基金 - 债券 - 黄金及其他商品 -
房地产或房地产收益权 - 其他有明确发行方、底层资产及法律结构的代币化资产

建议展示字段： - 资产名称、简称、类别 - 底层资产及权利类型 -
发行方及法律文件链接 - 发行/交易所在链 - 代币合约地址及区块浏览器链接 -
可交易市场或平台 - 外部交易链接 - KYC/地区限制提示 -
数据来源、最后更新时间、核验状态 - 风险提示与权利边界说明

建议采用"资产（Asset）"与"市场（Market）"分离的数据结构： -
一个资产可以在不同市场或链上拥有不同的交易入口。 -
资产身份、法律权利、发行方信息与市场流动性不可混为一谈。 -
不能因代币名称相同就认定其代表相同法律权利或底层资产。

MVP 建议： 1. 从经过核验的有限资产清单开始。 2.
只展示能找到可靠来源的项目。 3.
以发行方、市场或区块浏览器的原始链接为优先证据。 4.
不展示未经核验的价格、交易量、流动性、合约地址或收益率。 5.
对地区限制、资格门槛及 KYC 要求作醒目说明。 6.
外部链接需定期检查，避免失效或指向仿冒站点。

历史代码线索：过去曾提到 `/rwa`
页面可能使用静态演示资产，`src/lib/aifi-data.ts` 曾有
`USTF`、`TPC`、`REITX`
等演示条目。它们不能据此被认定为真实、已核验或可交易资产；需检查当前仓库后才能确认。

### 2.4 Web3 Infrastructure

当前不应假定所有能力都已上线。钱包连接、签名、支付和交易执行应有明确的权限边界，并避免让用户误以为平台托管资产或为外部协议背书。

## 3. 产品边界与监管风险

### 3.1 MVP 明确不做的功能（历史讨论边界）

-   不在平台内提供 Swap 交易执行。
-   不自建订单簿或撮合系统。
-   不托管用户资产。
-   不自行发行 RWA 代币。
-   不管理 LP 或流动性池。
-   不自建证券交易所。
-   不在缺乏可靠来源时宣称资产价格、收益、流动性或合规性。

这些是产品范围控制，不是法律结论。是否构成受监管活动，需要结合实际交互、费用、用户所在地区、资产性质、营销话术、交易路径和合作方关系进行专业评估。

### 3.2 需要持续检查的风险

-   RWA
    代币可能对应证券、基金份额、债权、收益权、商品权益或仅是合约层面的代币，不能一概而论。
-   用户连接钱包或点击外部链接，不代表其具备购买资格。
-   "非托管""信息平台""仅提供链接"等描述不能单独决定监管定性。
-   应避免保证收益、暗示无风险、混淆代币与法律所有权。
-   应建立项目/发行方核验流程、投诉与下架机制、风险披露和链接检查机制。
-   如对交易、推荐、分销、引流或成交收取费用，应单独评估其监管与合同影响。
-   应按目标地区评估制裁、KYC/AML、消费者保护、隐私、数据安全与广告要求。

### 4.3 开发原则

-   先检查仓库与运行状态，再提出改动；不要凭旧摘要猜测代码。

-   将 UI、数据模型、数据源适配器和外链校验逻辑分层。
-   区分演示数据、待核验数据和已核验数据，并在 UI 中标明。
-   不把 API 密钥、私钥或敏感凭据放入客户端代码或提交到 Git。
-   涉及钱包签名、交易、支付、Agent
    自主操作时，采用最小权限、清晰确认与可审计日志。
-   对外部 API 设计超时、错误状态、缓存、速率限制和数据更新时间。
-   所有"已完成""已部署""已集成"的描述必须有当前仓库、部署或运行证据。

### 5.4 数据状态建议

统一采用清晰的状态，例如： - `demo`：仅供演示 - `unverified`：尚未核验 -
`verified`：已根据定义好的证据标准核验 -
`stale`：数据过期，需要重新核验 - `delisted`：已下架或不再推荐

"已核验"应定义具体标准，例如发行方官方文件、合约地址与区块浏览器一致、市场链接属于可信官方域名等，而不能仅凭项目自述。

## 6. Uniswap 与交易集成策略

历史讨论曾比较 Uniswap API 与 v4 SDK。对当前"RWA Discovery
以发现与外链为主"的 MVP： - 不需要为了展示资产而集成 Uniswap Trading
API。 - 不需要为了发现页面而直接引入 Uniswap v4 SDK。 -
先做好资产、市场、合约地址、交易链接与核验状态的数据治理。 -
只有在明确产品需求、资产适用性、链支持、用户地区和合规边界后，才评估交易执行或协议集成。

如果未来增加链上交易功能，需要重新评估钱包签名、交易模拟、滑点、代币风险、授权撤销、交易失败、链选择、用户确认及监管风险；不可将其视为简单的前端按钮。

## 11. 给后续 AI/开发工具的协作规则

1.  **先区分事实、决定、设想与未知。** 不把讨论过的功能说成已完成。
2.  **先检查当前代码，再建议代码修改。** 不从旧记忆推断文件现状。
3.  **不要虚构链上数据。**
    合约地址、价格、交易量、流动性、发行方和可交易状态都需要可靠来源。
4.  **保持产品范围克制。**
    优先交付一个完整的用户流程，而不是同时铺开所有生态模块。
5.  **对监管风险保持准确表述。**
    产品边界有助于降低复杂度，但不能替代法律意见。
6.  **使用中文解释产品决策。** 技术标识、代码、协议名和 API
    名称保留原文。
7.  **修改前列明影响范围；修改后列明变更、测试与未解决问题。**
8.  **不声称已推送、部署或集成，除非工具结果明确证明成功。**
9.  **保留决策记录。**
    每项重要决策建议包含日期、决定、原因、替代方案、风险与复核条件。
10. **不要将本文视为完整历史聊天导出。**
